# Approved proposal → one native worker

This source slice reuses manual_runner; it does not introduce a scheduler, task state machine, worktree allocator, budget broker or model transport.

`approval.py capture` verifies a Hermes receipt's content digest, fixed identity, current policy, admitted validation/paths/limits and clean registered canonical baseline. It snapshots the request, baseline, session configuration hashes and runner hashes into a root-private review record. Installation acceptance proposals are explicitly refused. Capturing a proposal grants no authority. Root operator `approve` requires an exact review digest and explicit one-execution flag; it creates an approval which never authorizes publication.

`approved_launch.py` validates protected records/config/code and policy freshness, dedicated UID996/group, private worker root and protected credential metadata. It never reads provider-key bytes. It refuses any loaded/unverifiable fixed `rras-coding-task.service` slot or existing engineering-UID process. Approval is exclusively consumed before staging/service contact; exceptions or lost responses never authorize retry. It creates an independent clone at the approved commit, removes the remote, gives UID996 only its own execution copy, and supplies root-owned read-only request/registry inputs. systemd LoadCredential delivers the key only into the worker.

The fixed transient service name serializes launches even when two operators race through preflight. The runner retains native lifecycle responsibility and verified-stop/scope/validation/evidence behavior. systemd controls process teardown. Root launch/submission/review/authorization references remain separate from worker evidence. A lost client may leave the service running; another production launch remains blocked while the slot exists or the UID is busy. No cancellation, recovery mutation, automatic retry, commit, GitHub publication, merge or deployment is implemented. Old ad hoc launch scripts bypass this entrypoint and must not be used for production concurrency; the trusted operator can always act outside the tool.

After an ambiguous failure, preserve approval/consumption/launch records, unit state and worktrees. Consumption is not proof of a model call. A missing result is not proof of termination. Root host-stop checks are conservative. Do not stop/adopt a service merely by planned name or delete an approval marker. Inspect systemd invocation evidence and UID/cgroup state; a fresh approval requires a new explicit operator decision. Native failed task states are not rewritten.

Production setup remains pending: reviewed source installation, root-private approval store, root-owned jobs parent with worker-readable per-job files, approved repository registry, guarded operator commands and source-pinned runtime. Preparation stdio has no approval/launch tool. Portal spending policy remains operator-controlled; no local hard budget claim. Session code/profile changes or policy changes invalidate pending reviews as appropriate.

Acceptance harness `probe_approved_launch.py` runs only with an exact synthetic manual_runner.py and harmless systemd credential. It tests root capture/approval, real cloning, actual systemd credential delivery to UID996, fixed-slot exclusion without consuming a second approval, host-stop verification and replay refusal. It contains no model client and no real provider key; production source is never replaced. Fixture job/work/control directories are isolated and retained. Operator-performed installed-systemd acceptance passed all nine checks with a synthetic worker, harmless credential and zero API calls. Actual service exit was0 and host stop verified. Production coding/session execution was not tested by this harness. Source integration tests use real Git/records with mocked service manager and fixture-only permission adapters; those do not establish a host boundary.

The reusable source [operator interface](operator-control.md) now accepts repository admission candidates through a separate protected capture adapter. Admission-bound reviews recheck live registration/configuration, exact work, control-code/schema hashes and named baseline in the underlying launcher immediately before consumption. Legacy Hermes receipt capture remains unchanged. The new interface requires isolated host acceptance and packaging before installation.
