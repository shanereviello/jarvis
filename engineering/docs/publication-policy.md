# Standing agent publication authorization

Operator decision2026-10-15: coding agents may push admitted coding changes to their own dedicated review branches and open/update draft PRs without requesting confirmation for each push. Human approval remains required for merge and deployment. Paid task execution approval remains separate.

`config/publication-policy.json` admits jarvis and robot_ws remotes. `publication_policy.py` plans only push/draft-PR actions for the exact task-assigned codex/ branch, after verified worker/host stop, successful validation/task outcome and admitted scope. Default branches, other tasks' branches, refspec/tag injection, force-push, branch deletion, merge and deployment are refused. Publication must occur through a trusted adapter; model arguments are not trusted evidence or branch assignment.

Proposal/execution receipts retain publication_authorized=false because those records do not grant remote authority. The separate operator-controlled standing policy supplies that authority to a publication adapter after its evidence checks. Do not change false to true in a Hermes-writable proposal. Failed tasks can retain local evidence without automatic publication.

Current state: publication policy/planner is source-tested, not an installed automatic publisher. The existing runner still leaves changes uncommitted. A trusted post-validation publisher must prepare/verify the review commit and use the planned exact refspec and admitted remote. GitHub credentials remain outside the coding worker; do not give a model a general SSH key/token or broaden coding-sandbox networking. Standard Git push must remain non-forced so an unexpected remote branch history fails safely.

No GitHub branch-protection rules, automation identity or credential permissions were changed by this source policy. A siloed branch alone does not restrict the powers of a general GitHub credential. For this internal workflow the trusted publisher's narrow interface is the intended boundary; repository protection/separate automation identity are upgrade points if stronger server-side enforcement is needed. The human operator can explicitly authorize a merge through a separate action. RRAS policy cannot override external tool/platform automatic approval review.

## Commit preparation slice

`tools/rras_native/publication.py` now prepares a review commit from a hash-bound export in a fresh clone of the reviewed canonical repository. It checks launch review/result binding, native task/run, baseline, request, artifact hashes, exact file scope, successful validation, and verified worker/host stop. New-file content comes from the retained base64 artifact. It refuses tracked symlinks/submodules and preserves any pre-existing publication destination. Local bare-remote tests demonstrate an exact review-branch push and refusal of divergent history without force.

This is an internal credential-free library, **not an installed publication service or an authentication boundary**. Its dictionary inputs and returned push arguments must stay within trusted operator code. An untrusted caller can fabricate dictionaries; hashes establish consistency, not provenance. `push_argv` constructs a non-forced command but does not authenticate, run Git, or open a PR. Partial preparation directories are retained on failure; use a new destination after investigation rather than deleting evidence automatically.

Before production use, the operator adapter must capture the root-owned launch review/result and the exact stopped worker export bytes into protected custody, verify their expected locations and ownership, assign the branch from the trusted run identity, and retain a publication receipt binding commit/export/remote/branch. It must recheck the prepared clone and policy immediately before authenticated push, with credentials available only to that process. Root capture must treat worker paths and content as untrusted, refuse symlinks and bounded-read each artifact once. A draft PR references the resulting branch; merge/deployment remain separately authorized. Do not install or run this library directly against worker-writable records.

`publication_capture.py` adds an administrator-only custody step. It requires the protected successful launch/result binding, checks the fixed service slot and UID are currently empty before and after reading, requires protected ancestors and regular UID996-owned files, limits artifact names/count/sizes, verifies hashes, and assigns `codex/task-<trusted-run-id>`. It reads each worker artifact once and retains a root-private copy plus a hashed capture receipt. Existing destinations are refused; partial captures remain for inspection. This step is not yet installed or host-accepted. Operate capture serially with launch; the two stop checks are observations, not an atomic lock spanning unrelated administrator operations. No automatic launch/capture concurrency or adversarial shared-UID claim is made.

Remaining integration: a protected-custody loader and revalidation immediately before commit/push; the operator-authenticated transport adapter and publication receipt; draft-PR creation; and a dedicated-UID model-free installed acceptance before real task use. The existing manual operator Git connection is the default publication identity for this internal workflow; unattended GitHub credentials have not been provisioned. Native worker access and model approval remain unchanged. These source slices do not claim the complete end-of-task review gate is deployed.

`probe_publication_capture.py` is the next administrator acceptance step. It creates only a new `/var/lib/rras-publication-acceptance-<uuid>` fixture, uses harmless bytes and real UID996 file ownership, and exercises protected custody plus changed-content, mode, owner, symlink and existing-destination refusals. It checks the current production slot is empty but never starts/stops a unit, accesses credentials, calls a model, pushes, or changes native task state. Its root-private `acceptance.json` is retained even on failure. This validates filesystem custody only, not a coding session, authenticated transport, or concurrent-launch locking. All fixture records remain; cleanup is unnecessary for process safety because no process/container is created. Do not recursively delete operational runtime roots to clean this fixture.

## Custody-to-transport integration

The operator-performed filesystem custody acceptance passed all ten cases (harmless bytes, no worker/model/service changes). This establishes the tested ownership/file checks; it does not establish authenticated GitHub transport.

`publication_custody.py` reads root-protected capture members once with size limits, verifies every recorded digest and run-derived branch, and passes captured bytes to commit preparation. Its separate prepared record stays outside the checkout. It makes no network calls. `publication_transport.py` is an internal trusted-operator API: it rechecks the admitted remote/refspec, clean exact commit/branch and single baseline parent before attempting a push. It refuses an existing remote branch rather than adopting it. It retains a started receipt before remote contact, then a publication/unknown outcome binding repository, branch, commit, baseline and export. A lost response or missing final receipt requires read-only remote inspection; it never automatically retries. No raw command output/error text is copied into that receipt.

The transport uses the invoking operator's SSH home/agent in batch mode, with provider credentials excluded from the environment. It provisions no credential and introduces no unattended GitHub identity. Keep the API inaccessible to the model: supplied dictionaries are not authenticated evidence. Installed orchestration must load protected custody and keep the prepared record/clone beyond worker write access. Transport receipts are operator-owned records; ledger indexing and root custody of final publication records remain later integration work.

It never contacts GitHub or launches a worker. Canonical production repos and installed services are untouched. The source test executes the same complete fixture with ownership/service checks mocked; the administrator test is needed to validate actual host permissions. Fixture records and the bare remote are retained under one fresh `/var/lib/rras-publication-workflow-<uuid>` directory; no process/container cleanup is needed.

## Root-to-operator handoff

Operator-performed custody-to-local-Git acceptance passed all seven cases: protected capture, verified review commit, exact branch publication, receipt, unchanged fixture canonical baseline, replay refusal, and no merge/deploy authority. This was a local model-free test; GitHub and provider credentials were not used.

`publication_handoff.py` bridges protected root evidence to the existing named operator's Git connection. Root verifies the prepared commit and current policy hash and creates a source-only Git bundle plus a narrow manifest in a fresh root-owned directory explicitly set to0555 (files0444). The bundle includes the review branch's complete reachable repository history; it excludes custody records and task logs. Repository admission must therefore remain appropriate for publishing that repository's history. The manifest contains commit/baseline/export/branch/remote and operator UID, with no private checkout paths or task logs.

The named operator imports the verified bundle into a new private workspace, removes its local clone remote, and publishes through the policy-selected exact remote/refspec. Root-owned package bytes are rechecked on each invocation. The worker UID and root cannot invoke the operator import/push path. No SSH key/token is copied, installed, read by RRAS, or passed to a worker. The invoking operator's existing SSH identity/agent supplies transport authentication. This is an operator command, not an unattended publisher or model-accessible MCP capability.

Existing files, installed services, secrets and production repositories are untouched. A partial fixture/review is preserved and never adopted or overwritten on retry.
