# Worked scenarios for design review

These are synthetic examples of proposed behavior, not executed work or live records.
No IDs/digests below are approvals or schema fixtures. Unknown means unknown.

## A. Managed documentation correction

1. Work W1/revision1 describes a repository documentation issue, exact baseline,
   allowed Markdown path, expected behavior and a whitespace-only validation limit.
2. Protected capture freezes document D1/version1 and its exact content/Markdown hashes
   together with the existing admission/config/profile identities.
3. Human reads that version and approves one managed execution against its capture.
4. Worker returns; protected stop/evidence and independent validation facts link
   attempt A1 to W1/revision1. Agent's rationale/result remains reported unless checked.
5. Completion D2 states actual changed file and rationale, validation scope, limitations
   and PR reference. Human acceptance, merge and deployment remain distinct events.
6. Later Jarvis answers 'why' from the curated intent/decision sections, and 'what'
   from exact commit/PR evidence. No deployment fact appears unless recorded.

## B. Interactive architecture work across sessions

1. Human and Codex create W2 with an interactive review document. No managed worker
   approval is required merely to record the conversation's engineering intent.
2. Session S1 inspects source and drafts alternatives. A checkpoint records what was
   inspected, what is proposed, and decision D1 still pending; no completed architecture
   acceptance is invented.
3. Human chooses an approach. The explicit decision links its exact proposal digest;
   if the only source is chat import, label human_reported and retain the source quote.
4. Session S2 attaches to W2 and the current revision. It sees the prior checkpoint,
   pending questions, approved scope and source baseline evidence; a changed checkout
   is recorded explicitly rather than treated as the previous exact state.
5. An implementation PR is linked. The completion document separates accepted design,
   tested implementation, merged code and uninstalled changes. Every statement has a
   source or is labeled a proposed/agent-reported conclusion.

## C. Repository handoff and interrupted capture

An interactive task spans repositories R1 and R2. Create W3 and W4 with a shared
initiative relation, not one work record changing repository. S3 selects active W3
before submitting a checkpoint. Intake is down; the local client reports pending
and retains a private bounded spool. The session crashes before a close event.
Later delivery records the original client key and unknown end state; duplicates
are idempotent and no success is inferred. A managed follow-on for W4 requires
separate admission, exact revision capture and one-use paid approval.
