# Linear-first onboarding: implementation status

The approved v0.5 architecture introduces onboarding; it is not yet a live end-to-end capability. The four new work items are REV-55 through REV-58, mapped to SHRR-09 through SHRR-12 and the owned v0.5 project. Existing v0.4 work and production policy pins remain intact.

The source provides draft project and work coordinators, a history adapter, additive schema-6 project and work reservations, an operation-scoped history access policy, and native planning-origin and issue verifiers. The coordinators never designate an architecture or grant execution. Their origin and issue verifiers and storage are injected trusted components; untrusted agent JSON is not itself proof. The history adapter's credential must be held by a dedicated broker that does not expose the raw history socket to the agent.

The reservation is immutable and unique by Linear organization/project and by owned project ID. Existing project-mapping submission checks a reservation inside its own transaction, so another mapping cannot claim the same identity under a different scope or project after a reservation commits. The schema-5-to-6 migration binds a fingerprint of prior data and schema to an explicit plan and preserves prior signed snapshots and evidence. A process can still fail between reservation, project creation, draft saving, and mapping; retries must reconcile exact IDs and bytes, and an unresolved conflict remains visible. Reservations are not approvals and cannot launch work.

The access v3 policy is additive: an explicitly configured planning-only peer has fixed agent, organization, teams and read scopes, no general history write grant, and can reserve identities, read permitted scoped data, create a reserved project and its first draft, and create and link proposed work against that draft. Work identity is reserved uniquely for its Linear issue and plan ID, and its membership points to the unapproved draft. This is a draft association, not architecture designation or execution authority. The peer cannot designate an architecture, submit unrelated ordinary work, or change a scope. The planning origin verifier accepts only a verified human-directed native context and configured scope resolution; its result explicitly does not infer human agreement. The issue verifier checks a separate native Linear response against the same app, organization, team and project.

Disposable tests cover draft and mapping replay, lost responses, concurrent conflicting reservations, prior history and signed snapshots, schema-6 evidence access, scope and actor refusal, operation-level denial, and a real same-UID Unix socket. Synthetic Node tests exercise the verifier in the existing n8n container. These do not establish a cross-UID host deployment or a live Linear flow.

The source also has a local create-once journal and coordinator for a proposed Linear issue: it checks the retained draft and plan, commits an intent before invoking a trusted create callback, verifies a returned issue, and links the history work. A retry never blindly repeats an uncertain create. An inactive n8n issue-creation candidate and optional draft-issue MCP tool are prepared; neither the workflow nor a Linear mutation is deployed. Resolving uncertain creations still requires a trusted reconciliation path.

A source-only planning dispatcher and short-lived session registry bind an agent peer to a dispatch and recheck its native identity and active state through injected trusted readers. A local Unix transport obtains the caller identity from the operating system; it has no registration operation. A planning MCP client exposes only draft project and draft work tools and fixes the dispatch at launch. The registry must be placed in protected service-owned storage. Production wiring must implement native verification, lifecycle and registration boundaries; these components alone do not authenticate an external request. A separate candidate builder checks exact project/work identities, evidence pins and non-overlapping runtime paths, without installing a policy or changing execution authority. Its history and Linear evidence verifier also remains to be connected.

Linear's documented third-party agent session entry points are mentions and issue delegation ([agent interaction](https://linear.app/developers/agent-interaction)); agents cannot be project members or leads ([agent setup](https://linear.app/developers/agents)). The proposed supported entry is therefore an agent mention or delegation on a planning issue belonging to the existing backlog project. The native read must resolve the issue's exact project; the planning issue does not itself become an implementation work item. The source contains an isolated unmapped-issue planning admission parser, but it is not connected to the active workflow or a planning runtime.

The [published Linear GraphQL schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/src/schema.graphql) does not expose the `isArtificialAgentSessionRoot` field used by an existing deployment-specific delegation-origin pattern. The new planning query omits it. A source-less session whose creator is merely a responsible human is rejected as ambiguous, because the schema says an automation may set that creator to the assignee. A direct human prompt or verifiable human-authored source comment is supported by the verifier. Safe first-event delegation remains an acceptance gap until the installed API's fields and origin semantics are independently checked; existing production ingress is unchanged.

An additive PostgreSQL planning queue, separate acknowledgement outbox, and routing function are prepared in source. In a network-isolated disposable database, tests cover duplicate delivery, changed content, planning/execution identity separation, generated dispatch and reconciliation SQL, and outbox state transitions while preserving normal mapped execution intake. The migration is not installed. Synthetic inactive ingress, dispatch, stop, reconciliation and outbound candidates exist; they require integrated n8n/native verification, actual stop delivery, uncertain-result recovery, and host acceptance before activation.

Inactive Codex origin and issue reader candidates now select a retained dispatch, make separate native Linear reads with the configured app identity, enforce fixed team and project-scope grants, and return only verified planning metadata. A loopback-only authenticated client and fixture tests bind issue reads to the original dispatch and origin. The workflow candidates are not installed and their GraphQL requests have not yet been verified against the live workspace.

A source-only read-only Codex planning runtime now takes a private exclusive journal lock, pins its policy, journals dispatch before starting a native thread, and retains uncertain outcomes across a restart. Its synthetic-client tests cover a follow-up resuming the same thread, a stop targeting the same session, and collection of bounded visible output while excluding reasoning and unrelated threads. The private runtime API and a native-context adapter verify the original dispatch and message, with a separate verified-stop path. Native service isolation, live origin and activity delivery, actual follow-up/stop delivery, replay reconciliation, and n8n delivery remain to be integrated and verified before use. The runtime cannot be considered deployable based on the synthetic test alone.

An additional model-free, network-isolated fixture starts the installed Codex App Server with the basic planning configuration, checks its complete inventory of two draft tools, and calls both through the planning broker against a disposable history database with synthetic native identities. It verifies that the draft architecture and work mapping are retained with no governing designation. The fixture uses one UID and does not establish a model turn, production host isolation, or live Linear/history writes.

A second network-isolated fixture runs the native planning calls using separate numeric UIDs for the native process and history broker, including synthetic issue creation followed by the draft work mapping. It confirms the native identity cannot read the private history database or issue journal and a third UID cannot call the broker. The fixture uses a shared synthetic group for socket traversal; production named-UID ACLs and service hardening still need separate host acceptance.

A protected service composition and an operator-only history adapter are prepared in source. The adapter can retain an independently verified human decision and designate the exact retained architecture; the verifier and protected operator service are not yet connected. A stale planning dispatch can be checked through its retained runtime status without re-dispatching it; a disposable PostgreSQL test covers uncertain and later completed outcomes. This recovery is not yet verified with deployed n8n and the actual runtime.

One source-only decision verifier supports an unedited native Linear comment containing an explicit version and digest, from a configured human on the reviewed issue and project. It consumes independent protected comment and review readers and retains the original text and its digest. These readers and the review store are not installed or live-verified. This narrow syntax is one possible attributable path; other approved direct conversations still need a verified source, and the planning agent cannot supply its own approval evidence.

An immutable operator-side review store now pins a separately verified Linear issue to exact retained architecture bytes and the current project head. A read-only native GraphQL comment adapter composes with the verifier and rejects incomplete results, edits, archival, bot, external and on-behalf-of attribution. Tests use synthetic GraphQL replies and disposable history; the authenticated GraphQL transport, protected operator service, review presentation, and real-source behavior are not yet deployed or verified. Linear notes that on-behalf-of attribution can be unavailable for inaccessible users, so this read alone cannot eliminate every attribution ambiguity; resolve that boundary before production authorization.

A source-only execution evidence verifier checks the governing document bytes, operator-decision designation, latest decision observation, current work and assignment, and execution mapping against one signed history snapshot. It requires separate trusted human-attribution, native Linear issue, and workspace-isolation checks. The verifier does not install policy; a future publisher must recheck under its own admission lock because a history snapshot is not a cross-service lock. Synthetic tests cover stale, revoked, mismatched, and unverified evidence; real transport, provisioning and integrated host acceptance are still pending.

A candidate workspace inspector verifies a fixed per-issue directory and socket, native ownership, standalone clean Git checkout, exact baseline and absence of remotes. The Git invocation avoids user/system config and hooks. It requires a separate sandbox-isolation verifier and grants no filesystem permission. Temporary repositories exercise refusal paths; real issue workspace provisioning, service isolation and the locked installation/recheck remain outstanding.

Still required: live verification of the protected broker's native Linear readers and scope resolver; the Jarvis planning entry; actual Linear issue creation and verified responses; operator decision/designation and safe execution admission; capture, crash/concurrency and security acceptance; and operator-approved deployment and live pilots. The decision coordinator and execution candidate in source still need trusted operator-verification and history-evidence integrations. No schema migration, service access policy, workflow, production agent permission, or production route has been changed by this source slice.
