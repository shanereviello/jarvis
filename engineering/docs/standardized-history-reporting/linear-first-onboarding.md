# Linear-first onboarding: implementation status

The approved v0.5 architecture introduces onboarding; it is not yet a live end-to-end capability. The four new work items are REV-55 through REV-58, mapped to SHRR-09 through SHRR-12 and the owned v0.5 project. Existing v0.4 work and production policy pins remain intact.

The source provides draft project and work coordinators, a history adapter, additive schema-6 project and work reservations, an operation-scoped history access policy, and native planning-origin and issue verifiers. The coordinators never designate an architecture or grant execution. Their origin and issue verifiers and storage are injected trusted components; untrusted agent JSON is not itself proof. The history adapter's credential must be held by a dedicated broker that does not expose the raw history socket to the agent.

The reservation is immutable and unique by Linear organization/project and by owned project ID. Existing project-mapping submission checks a reservation inside its own transaction, so another mapping cannot claim the same identity under a different scope or project after a reservation commits. The schema-5-to-6 migration binds a fingerprint of prior data and schema to an explicit plan and preserves prior signed snapshots and evidence. A process can still fail between reservation, project creation, draft saving, and mapping; retries must reconcile exact IDs and bytes, and an unresolved conflict remains visible. Reservations are not approvals and cannot launch work.

The access v3 policy is additive: an explicitly configured planning-only peer has fixed agent, organization, teams and read scopes, no general history write grant, and can reserve identities, read permitted scoped data, create a reserved project and its first draft, and create and link proposed work against that draft. Work identity is reserved uniquely for its Linear issue and plan ID, and its membership points to the unapproved draft. This is a draft association, not architecture designation or execution authority. The peer cannot designate an architecture, submit unrelated ordinary work, or change a scope. The planning origin verifier accepts only a verified human-directed native context and configured scope resolution; its result explicitly does not infer human agreement. The issue verifier checks a separate native Linear response against the same app, organization, team and project.

Disposable tests cover draft and mapping replay, lost responses, concurrent conflicting reservations, prior history and signed snapshots, schema-6 evidence access, scope and actor refusal, operation-level denial, and a real same-UID Unix socket. Synthetic Node tests exercise the verifier in the existing n8n container. These do not establish a cross-UID host deployment or a live Linear flow.

The source also has a local create-once journal for a proposed Linear issue: it commits an intent before invoking a supplied trusted create callback, verifies a returned issue, and treats a lost or ambiguous result as uncertain. A retry never blindly repeats the creation. This component is not yet connected to an n8n workflow or a deployed Linear mutation, and resolving uncertain creations still requires a trusted reconciliation path.

Still required: a protected cross-process verifier/broker with a trustworthy native Linear read and explicit scope resolver; planning-only Jarvis and Codex runtime entry points; actual Linear issue creation and connection of the verified responses; operator decision/designation and safe execution admission; independent crash/concurrency and security acceptance; and operator-approved deployment and live pilots. The decision coordinator in source still needs a trusted operator-verification integration. No schema migration, service access policy, workflow, production agent permission, or production route has been changed by this source slice.
